# DeepSeek Harness 通用执行纪律与实测门禁

## 1. 先对齐需求边界，再执行不可逆改动
- 当目标存在明显技术分岔、背景尚在补充或操作不可逆（删除数据、覆盖配置、发布产物）时，先简明列出关键分岔点并给出推荐默认项，确认后再动手。
- 当任务范围已明确且授权清晰时，完整闭环执行，避免无意义的反复请示。

## 2. 改动白名单与语义事实核验
- 修改现有项目或配置文件（如 `cordis.patch.yml`、`.dsh/mcp.json` 或业务代码）前，先读原件、锁定需改动的文件清单，不顺手重写无关模块。
- 对接外部接口、配置文件字段或数据指标时，不能只用非空断言判定成功；必须核对真实字段定义与宿主运行输出，发现冲突先查底层事实。

## 3. 长程多步骤任务状态落盘（Anti-Drift Checklist）
- 面对超过 3 个主要阶段的工程建设、重构或研究任务，先在工作区或临时目录落盘分阶段检查表（如 `task_plan.md`）。
- 每完成一个阶段及时核对勾选；收尾前逐条对照用户最初需求与验收标准，避免遗漏子项。

## 4. 真实用户入口端到端验证
- 仅做静态语法检查不能等价于产物可用。
- 凡交付给用户直接双击或调用的脚本、CLI 命令、MCP 服务或配置文件，必须通过真实命令执行冒烟与功能验证，确认退出码与输出符合预期；若受环境限制无法覆盖某项，如实说明未验证边界。

## 5. 遵守 Rosetta 技能库审批与同步机制
- 提议新增或修订 Rosetta 技能卡时，一律通过 `rosetta_propose` 提交待审草稿（或凭用户签发的单次授权码调用 `rosetta_apply_authorized`），不要直接手改 `catalog/skills/` 磁盘文件导致全包 SHA-256 校验触发漂移冻结。
- 提醒用户：DeepSeek Harness 按会话缓存技能列表；首次同步或增删技能后，需新开会话或重载 DSH 使最新技能目录生效。
